# GATE 1B REPORT: Cryptographic Authentication Verification and Session Trust Hardening

## 1) Executive summary

Gate 1B hardens the identity federation and passkey paths so that sessions cannot be established without cryptographically verifying the provider response. The implementation uses maintained libraries (`jose` for OIDC/JWKS, `@simplewebauthn/server` for WebAuthn), enforces fail-closed configuration, validates nonce/redirect/state where applicable, and binds passkey challenges to accounts with single-use atomic consumption. The Gate 1A kill switches remain in place (Google/Apple/Passkey disabled by default); OAuth and Passkey now perform real verification when enabled. All authentication paths still go through `AuthService.resolveOrCreateUserAndSession` and the existing session rotation/replay-detection flow (Gate 04) remains intact.

## 4) OAuth verification implementation and evidence

**Implementation:**

- `GoogleOAuthProvider` / `AppleOAuthProvider` require explicit audience allowlist and issuers; fail closed if unconfigured.
- `verifyIdentityToken` uses `jose.jwtVerify` with `algorithms` pinned to allowlists (`Google: RS256,ES256`, `Apple: ES256`), `issuer`/`audience` validated by `jose`, `clockTolerance: 5`, `maxTokenAge: '10 minutes'`. Rejects missing `sub`, validates `azp` if present against allowlist.
- Nonce: if `expectedNonce` provided, claim must match raw or (Apple) SHA-256 hex of raw nonce. Logs warnings without token material.
- Authorization code flow: `exchangeAuthorizationCode` posts to provider token endpoint with `grant_type=authorization_code`, includes `code_verifier` (PKCE) and `redirect_uri` (required; must be in exact-match allowlist), optional `client_secret`. Apple secret generated as short-lived ES256 JWT from `APPLE_SIGN_IN_*` or taken from `APPLE_OAUTH_CLIENT_SECRET`. Network/HTTP failures logged without response bodies; fail closed.
- JWKS cached via `JwksKeyService` with `jose.createRemoteJWKSet` (`cooldownDuration 30s`, `cacheMaxAge 10m`, `timeoutDuration 5s`).

**Evidence (code):** `apps/api/src/modules/auth/providers/oauth.provider.ts` (verification, exchange, nonce, allowlists). Config: `packages/config/src/server-env.ts`, `apps/api/src/config/app-config.service.ts`.

## 5) WebAuthn verification implementation and evidence

**Implementation:**

- `PasskeyService.createRegistrationOptions` uses `generateRegistrationOptions` with configured `rpID`, `rpName`, `attestationType`, `authenticatorSelection` (residentKey/userVerification), stores challenge bound to `userId` + `purpose: 'registration'`, `expiresAt`, TTL from config.
- `PasskeyService.verifyRegistration`: atomically consumes challenge via conditional update (`consumed_at IS NULL`); verifies challenge belongs to requesting user; calls `verifyRegistrationResponse` with `expectedChallenge`, `expectedOrigin` (array), `expectedRPID`, `requireUserVerification`; extracts credential from `verification.registrationInfo.credential` (public key stored as base64url), checks uniqueness by `credentialId`, persists verified material.
- `PasskeyService.createLoginOptions` uses `generateAuthenticationOptions` (RP ID, userVerification, timeout), stores challenge with `purpose: 'authentication'` and `userId: null` (discoverable flow), returns allowCredentials from library if present.
- `PasskeyService.verifyLogin`: atomically consumes challenge; looks up credential by ID; builds `WebAuthnCredential` from stored public key/counter/transports; calls `verifyAuthenticationResponse` with `expectedOrigin`, `expectedRPID`, stored credential, `requireUserVerification`; enforces counter monotonicity (`newCounter > counter` when counter > 0) as clone detection; updates counter, `lastUsedAt`, flags.
- All failures throw generic exceptions; errors logged without token/credential material.

**Evidence (code):** `apps/api/src/modules/auth/providers/passkey.service.ts`. Schema/migrations exist (`passkeys`, `passkey_challenges`). Contracts updated in `packages/api-contracts/src/auth/auth.contract.ts`.

## 6) Session issuance and account-linking checks

- **Verification before session:** OAuth → verified by provider before `AuthService.loginWithGoogle/Apple`. Passkey login → `PasskeyService.verifyLogin` verifies assertion before `AuthService.createSessionForPasskeyUser`. OTP/Email verified via HMAC before session creation. All flow through `resolveOrCreateUserAndSession` / `createSessionForPasskeyUser` (session issuance only after verification).
- **No bypasses found:** All public OAuth/Passkey endpoints go through controllers that still enforce `assertProviderEnabled` (kill switches) and call the verified providers/services. No alternate controllers/legacy/dev/fallback paths added that skip verification. Firebase uses `firebase-admin.verifyIdToken`.
- **Account linking:** Linking behavior remains unchanged (existing `user_identities` mapping by provider+providerSubject; creation only on new identity inside transaction). Email from verified tokens is stored/propagated as-is but **not** treated as proof to link accounts without provider verification; no new linking logic based solely on unverified emails was added. Apple private relay emails are handled as returned by verified token.
- **Session/refresh compatibility:** `SessionRepository` rotation with row lock and token history replay detection unchanged. `AuthService.refreshSession` still checks account status and revocation. Gate 1A protections intact.
- **Revocation/suspension/deletion:** `AuthGuard` enforces session/user status; `logout`/`logoutAll`/revoke endpoints exist; account deletion marks user DELETED, hides profile, removes devices, revokes sessions.
- **Enumeration resistance:** `checkIdentifier` retains timing normalization; OAuth/Passkey errors are generic (no account-existence disclosure). Auth failures logged with non-sensitive context.
